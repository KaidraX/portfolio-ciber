Empire: LupinOne — do recon ao root

VulnHub · Empire #1 MÉDIO web enumfuzzingBase58SSH key crackingPython library hijacksudo/pip

Uma box temática do ladrão de casaca Arsène Lupin: nada vem de graça. A cadeia é um pequeno assalto — passar pelo robots.txt, arrombar um dotfile, tirar uma chave privada de um disfarce em Base58 e sair do prédio com o root.txt. Abaixo, do recon ao root, com o porquê de cada passo.

1. O alvo

Box Empire: LupinOne (VulnHub), de icex64 & Empire Cybersecurity — primeira da série “Empire”, dificuldade média. Vem como .ova para rodar offline em VM.

Classes exercitadas: enumeração web, fuzzing de diretório/arquivo, decodificação Base58, quebra de passphrase de chave SSH, hijack de biblioteca Python e abuso de sudo via pip install.

2. Recon

Como é uma VM local em rede host-only, o primeiro passo é achar o IP. Usei netdiscover no segmento e depois um nmap completo:

sudo nmap -A -Pn -sV -sC -p- --min-rate=1000 10.0.2.12

Superfície enxuta: 22/tcp OpenSSH 8.4p1 e 80/tcp Apache 2.4.48. O http-enum já apontou /robots.txt, um /image/ com listagem aberta e o /manual/ padrão. A home só tinha o desenho do Lupin de cartola — tema bonito, nenhuma porta óbvia.

3. robots.txt e o truque do ~

Quando a app é vazia assim, o /robots.txt é o primeiro lugar — autores de CTF adoram plantar pista ali. E tinha: Disallow: /~myfiles.

O prefixo ~ é um tell: é a convenção do mod_userdir do Apache, que expõe o diretório pessoal de um usuário como /~usuario/. Ou seja, o formato é a pista — mas o nome myfiles em si era isca: /~myfiles/ devolvia 404. O diretório real existe, só tem outro nome.

4. Fuzzing do diretório de usuário

Sabendo o formato /~algo/, o problema vira força bruta de nome. Usei o ffuf filtrando os 403 pra cortar ruído:

ffuf -w .../directory-list-2.3-medium.txt \
     -u http://10.0.2.12/~FUZZ -fc 403

Saiu um hit: secret. Em /~secret/, um bilhete do usuário icex64 dizia ter escondido ali uma chave privada SSH, com uma passphrase “segura contra a fasttrack” — uma wordlist famosa por ser curtíssima. (Spoiler: não era segura.) Arquivo escondido em diretório conhecido também é problema de fuzzing — desta vez mirando dotfiles com extensões:

ffuf -w .../directory-list-2.3-medium.txt \
     -u http://10.0.2.12/~secret/.FUZZ -fc 403 -e .php,.txt,.html

Repare no ponto antes de FUZZ (.FUZZ): é assim que se caça arquivo oculto. Resultado: .mysecret.txt.

5. Decodificando a chave

Baixei o arquivo e vi um blob alfanumérico longo, sem +, / ou =. Esse detalhe importa: a ausência desses caracteres já descarta Base64 padrão.

O Base58 usa um alfabeto reduzido — tira justamente os caracteres ambíguos (0, O, I, l) e os símbolos +///=. É o mesmo encoding de endereços Bitcoin. Logo, blob “limpo” desses símbolos é um forte palpite de Base58, confirmado num identificador de cifra.

Jogando no CyberChef com a receita From Base58, saiu uma chave privada OpenSSH. Salvei como id_rsa e tranquei a permissão (chmod 600, senão o SSH recusa a chave).

6. Quebrando a passphrase

A chave era protegida por passphrase. Um detalhe prático: dependendo do build do John, o formato moderno de chave OpenSSH dá erro de libcrypto. A volta é converter para o PEM antigo com o puttygen (pacote putty-tools):

puttygen id_rsa -O private-openssh -o id_rsa_fixed
chmod 600 id_rsa_fixed
ssh2john id_rsa_fixed > john_id

O ssh2john converte a chave cifrada num hash que o John entende: ele não “abre” a chave, apenas tenta cada palavra da wordlist como passphrase até derivar a chave corretamente. É cracking offline — não toca no alvo.

Como o icex64 jurou que a fasttrack.txt não pegaria, foi a primeira que testei. Em segundos saiu: P@55w0rd!. Lição real: confiança numa wordlist curta vale zero — “eles nunca vão adivinhar” é a frase que precede quase todo comprometimento.

7. Foothold — icex64

ssh icex64@10.0.2.12 -i id_rsa_fixed
cat user.txt

Primeira flag na mão.

8. Movimento lateral — icex64 → arsene

Primeiro reflexo em shell novo: sudo -l.

(arsene) NOPASSWD: /usr/bin/python3.9 /home/arsene/heist.py

Posso rodar um script Python específico como arsene, sem senha. O heist.py só faz import webbrowser e abre uma URL. E aí veio o pulo do gato:

ls -la /usr/lib/python3.9 | grep webbrowser
-rwxrwxrwx 1 root root ... webbrowser.py

Python resolve import procurando o módulo no seu caminho de busca (sys.path), e webbrowser é um módulo da biblioteca padrão que mora em /usr/lib/python3.9/webbrowser.py. Esse arquivo estava gravável por qualquer um (rwxrwxrwx — CWE-732). Então, quando heist.py faz import webbrowser rodando como arsene, ele carrega e executa o conteúdo desse arquivo — que eu controlo. É o clássico library hijack: o código roda com o privilégio de quem importa, não de quem escreveu.

Coloquei um listener (nc -lvnp 1234), adicionei uma reverse shell no topo do webbrowser.py e disparei a regra do sudo:

sudo -u arsene python3.9 /home/arsene/heist.py

O import executou meu código e voltou um shell como arsene. Estabilizei com python3 -c 'import pty; pty.spawn("/bin/bash")'.

9. Escalada — arsene → root

De novo sudo -l, agora como arsene:

(ALL : ALL) NOPASSWD: /usr/bin/pip install *

Primitivo conhecido do GTFOBins. O pip install de um diretório local executa o setup.py do pacote durante a instalação. Se o pip roda como root, o setup.py roda como root. O curinga * na regra permite passar qualquer caminho — inclusive um pacote forjado por mim.

A receita padrão do GTFOBins cria um pacote mínimo cujo setup.py abre um shell, e manda o sudo pip install processá-lo:

TF=$(mktemp -d)
echo "import os; os.execl('/bin/sh','sh','-c','sh <\$(tty) >\$(tty) 2>\$(tty)')" > $TF/setup.py
sudo pip install $TF

No instante em que o pip processou o diretório, caí num shell root — id confirmou uid=0(root) e o root.txt estava em /root/.

Como eu fecharia isso

  • webbrowser.py world-writable (CWE-732): módulo de biblioteca padrão jamais deve ser gravável por usuário comum. Permissão correta é root:root 644. Esse é o bug que derruba todo o lateral.
  • Regra sudo com curinga/pip: NOPASSWD: pip install * é entregar root. Nunca autorizar via sudo binários que executam código arbitrário (pip, python, editores, interpretadores) nem usar curingas. Se precisar, restringir a um pacote/caminho fixo e validado.
  • Rodar script de outro usuário como ele: a regra (arsene) python heist.py só é segura se todo o que o script importa for imutável pelo chamador — o que não era o caso.
  • Segurança por obscuridade: esconder a chave num dotfile e confiar numa passphrase fraca não protege nada. Chave privada não fica em servidor web; passphrase forte e única.

Classes exploradas

  • Enumeração web + fuzzing — robots.txt, mod_userdir, ffuf de diretório e de dotfile.
  • Encoding — reconhecer Base58 pela ausência de +//=.
  • Credential cracking — ssh2john + conversão de formato de chave.
  • Python library hijack — módulo da stdlib gravável (CWE-732).
  • Abuso de sudo — pip install executando setup.py como root (GTFOBins).
